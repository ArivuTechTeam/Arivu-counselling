# 24-Sep-2026

## new-change

Phase 6.4 - Extended objective question types. Additive and gated behind
`EXTENDED_QUESTION_TYPES_ENABLED` (default off): with the flag off, teachers
cannot request the new types, generation is byte-identical, and the five existing
types are unchanged. Descriptive/manual grading is intentionally excluded and
reserved for the future Mock Test Paper feature.

1. Three new auto-graded question types

   - Before: Quiz generation supported five objective types (single choice, multiple choice, true/false, numerical, fill-in-the-blank). Common exam formats such as assertion-reason and matching could not be produced or graded.
   - After: Added three objective, auto-graded types end-to-end (generate -> teacher review -> student take -> grade): **Assertion & Reason** (single-choice with the four standard options), **MRM** (multiple-response with partial credit, reusing the Phase 6.2 partial-marking engine), and **Matching** (pair each left item to a right item; dropdown UI; partial credit per correct pair). Each type is wired through the generation prompt spec, strict shape validation, deterministic grading, the teacher review card, the student take screen, and the answer formatter. Migration 59 appends the three values to the `question_type` enum (additive; no table or row changed).

2. Flag exposure to the browser

   - Before: The generation type picker was a fixed list, and the browser had no signal for whether the new types were enabled.
   - After: The `/me/profile` response now also carries `extended_question_types` in its `features` block (kept out of the commerce tenant-feature registry so it stays a separate rollout switch). The teacher generation picker shows the three new types only when that flag is on; otherwise the picker is exactly the five existing types.

3. Integration with the tenant-feature rollout on main

   - Before: This work branched before the tenant-scoped feature-flag system and the commerce-platform-default migrations landed on main.
   - After: Rebased onto the integrated main. Resolved the `/me/profile` and dashboard-profile conflicts by adopting the upstream `features: dict[str, bool]` shape and injecting the extended-types toggle at the response site rather than in the commerce registry, so the commerce feature invariants (and their migration-58 sync test) are untouched. Migration renumbered to 59 (main had already taken 57 and 58).

   Validation: 740 backend tests passing (116 subtests) and a clean frontend typecheck. The only non-passes are the pre-existing Windows-only cp1252 failures reading older migration `.sql` files, unrelated to this work. A generation failure seen during local testing was diagnosed to intermittent Supabase read timeouts (raise `SUPABASE_READ_TIMEOUT_SECONDS` locally), not this feature - the exact matching+single-choice request reproduced successfully. Activation requires applying migration 59 and setting `EXTENDED_QUESTION_TYPES_ENABLED=true`, then restarting the backend.
