# 23-Sep-2026

## changes-pavyaa

Phase 6.3 - Commerce Vertical Pack. Everything below is additive and gated behind
`COMMERCE_PACK_ENABLED` (default off): with the flag off, generation, extraction,
and verification retain their previous behavior, so generic tenants are
unaffected. The current flag is deployment-wide, not a tenant-specific switch.

1. Numeric-check registry (P6.3-A)

   - Before: A generated numerical question's answer was trusted as written; there was no independent check that the stated answer actually followed from the numbers in the question, so wrong AI arithmetic could be auto-verified.
   - After: Added a bounded registry of tested, currency-agnostic commerce calculators (simple/compound interest, straight-line depreciation, break-even units, percentage, ratio). When the pack is on, the generator may emit an optional `calc` (family + inputs) for a numerical question; verification independently recomputes with our own audited code and, on a mismatch, routes that question to teacher review with a `numeric_check_failed` note. The AI never grades its own maths and no model-produced code is ever executed; unsupported families are `not_checked`, never a false pass. New `numeric_checks` service + `calc` field on the generated-question model + verification hook, all no-ops when off. 40 new tests.

2. Numeric & table extraction fidelity (P6.3-C)

   - Before: PDF financial tables (balance sheets, trial balances, ledgers) were linearised by vertical position, so columns could interleave and a value could bind to the wrong row label; long documents could also be truncated mid-number.
   - After: When the pack is on, PDF pages run through table detection: each detected table is rendered as aligned pipe rows and its raw characters are removed from the surrounding prose, so each figure stays with its row label. Every failure mode (no tables, detection error, empty rows, unsupported page) falls back to today's plain extraction, so a page is never degraded and a generation never fails. Material truncation is pulled back to the last complete token so a figure like `1,00,000` or a table row is never split. Byte-identical when off. 13 new tests.

3. Paper profiles (P6.3-D)

   - Before: A course had no record of which exam, assessment year, jurisdiction, or accounting framework it targets, so there was no single place commerce context could live.
   - After: Added migration 56 after integration renumbering (`paper_profiles`: course level -> exam body / level / paper / assessment year / framework, one per course level, tenant-safe RLS and service-role grants). New admin-only API (`GET/PUT /api/v1/paper-profiles`) and an institution-admin "Paper profiles" screen to fill each course level in. Added a flag-gated `deployment_check` probe. Inert data when the pack is off.

4. Commerce context in generation (P6.3-B)

   - Before: Generated commerce questions could mix figures from different assessment years or frameworks, and a syllabus change could silently invalidate old questions.
   - After: When the pack is on and a course has a paper profile, generation appends a compact `COMMERCE CONTEXT` line to the prompt (e.g. "exam ICAI Foundation Paper 4; assessment year 2025-26; framework Indian GAAP") pinning year- and rule-specific figures to the stated period/framework. Context is resolved in the generation callers and passed into the payload builder as a parameter, so `generate_and_persist_from_material` stays a pure builder with no DB reads before the atomic commit (an existing invariant, guarded by tests). The prompt is byte-identical and no lookup runs when off or when a course has no profile. New `commerce_context` service + prompt param. 12 new tests.

   Historical branch validation recorded 653 backend tests and a clean frontend typecheck. Integrated validation is tracked in the merge result. Activation requires applying migrations 54–56 and setting `COMMERCE_PACK_ENABLED=true` (and `SCORING_POLICIES_ENABLED=true` for official exam scoring), then restarting the backend and filling paper profiles per course level.
