# 8-Sep-2026

## feature/ui-polish-and-branding

1.

   - Before: Loading, error, and empty states were bare across roughly thirty pages — errors as raw red text, loading as plain "Loading…", and empty lists as a single grey line — so the app felt unfinished and "AI-generated."
   - After: Shared `ErrorCard` (icon + message + retry), `Skeleton` presets, and an upgraded `EmptyState` (icon, title, message, CTA) were added and every role's pages were retrofitted onto them, replacing the bare states and the "flash of zeros" before data loads.

2.

   - Before: Machine tokens such as `pending_review`, `needs_edit`, and `{variant_type}` and raw `JSON.stringify` answer objects leaked into the teacher and student UI.
   - After: A shared `lib/format` provides `statusLabel`, `typeLabel`, and `formatAnswerValue`, so users see friendly labels and never a raw JSON blob.

3.

   - Before: The login page had non-functional `href="#"` Terms, Privacy, and "Forgot password?" links; admin and user deletion used the browser `window.confirm`; temporary passwords were shown in plaintext; and course/quiz tools used emoji as UI icons.
   - After: Dead links were removed (forgot-password became a "contact your admin" note), destructive actions use styled confirm modals, temporary-password fields have a masked reveal toggle, and emoji were replaced with an inline SVG icon set.

4.

   - Before: The ArivuPro logo was small and low-quality in the sidebar, login, and signup, with no product identity.
   - After: A reusable `Brand` lockup (crisp logo plus a "Quiz Platform" mark) is used consistently across the sidebar, login, and signup.

5.

   - Before: The Daily Challenge streak tracker used a rolling weekday window (so it "started on Tuesday") and looked plain, and the quiz/challenge result cards were basic.
   - After: The tracker is a fixed Sunday-to-Saturday calendar week with a richer streak hero and hover interactions, and the score and challenge cards became branded, downloadable images built only from real data.

6.

   - Before: There was no single technical reference for a new contributor to understand the whole system.
   - After: A detailed project technical document (architecture, stack, database schema, and features) was added.

## auth-pavyaa

1.

   - Before: Public signup let the browser choose its own role, and the `handle_new_user` trigger trusted that value, so a user could self-assign teacher, institution_admin, or super_admin, or place themselves in another institution's tenant.
   - After: Self-signup is students-only and enforced in the database — role and tenant for admin-created users come from trusted `app_metadata` (service-role only), and the hardened trigger forces `role = student` for a self-signup and only into a tenant flagged `allow_self_signup`.

2.

   - Before: A teacher was mapped to a whole course and automatically received every subject in it, which was too permissive, and an admin could not assign a teacher to specific subjects.
   - After: A `teacher_subjects` table (admin/super-admin managed) is now the source of truth for a teacher's subject access, a backfill preserved every existing teacher's current access, and the admin Users page gained a per-teacher "Subjects" assignment modal.

## extraction-pavyaa

1.

   - Before: Teachers could only generate quizzes from subject material; an existing quiz document (typed PDF, scanned image, or DOCX) had to be re-typed by hand.
   - After: Quiz extraction was added — Gemini reads the document directly (vision for PDF/images, no OCR) and extracts the questions, options, and answers into a draft quiz set (`pending_review`) that flows through the existing teacher review and publish pipeline.

2.

   - Before: Extracted quizzes were not filed under a chapter and appeared to students with unhelpful titles like "… — Extracted."
   - After: Extraction now requires and validates a chapter, maps that `chapter_id` onto the quiz set and every extracted question, titles the quiz with the chapter name, and the student quiz cards show a "Subject · Chapter" line.

3.

   - Before: Re-uploading the same document silently created duplicate quizzes, and courses or subjects could be duplicated by name.
   - After: A SHA-256 content-hash guard detects an identical re-upload and shows a soft "extract anyway" warning (never a hard block), and course/subject creation is get-or-create with database unique-index backstops.

## document-pavyaa

1.

   - Before: A teacher had no way to see what they had uploaded, when, under which subject and chapter, or to open the original file again.
   - After: A "Document log" page (route `/dashboard/teacher/documents`, added to the sidebar under Content) lists every upload newest-first with Document, Subject·Chapter, Uploaded, Quiz status, and Action columns, backed by a tenant- and owner-scoped `GET /api/v1/documents/log`; each row opens the original via a short-lived (300s) signed URL from `GET /api/v1/documents/{id}/file-url` that never exposes the storage path.

2.

   - Before: The log could only show the document's processing status (e.g. "completed"), which was misread as "a quiz was generated."
   - After: A new nullable `quiz_sets.document_id` link (migration-23, FK to `documents`, `ON DELETE SET NULL`, indexed) is recorded by both the generation and quiz-extraction services, so each row computes a truthful quiz status from the quiz set and latest extraction job: published, draft (in review), extracting, failed, or none.

3.

   - Before: If an extraction failed (for example the AI timed out) the teacher hit a dead end and could not easily re-run it, because re-uploading the same file was blocked as a duplicate.
   - After: The document is filed under its chapter at the start of extraction so a failed document keeps its chapter, and a new tenant- and owner-scoped `POST /api/v1/quiz-sets/{document_id}/re-extract` reuses the already-stored file and chapter (no re-upload, no duplicate block); a "Try again" button now appears on failed rows in the Document log and on the Extract-quiz form itself.

4.

   - Before: Every PDF, even a fully typed one, was sent to Gemini vision as base64 images with thinking enabled, no fallback, and a hard 180s client timeout, so large or typed PDFs timed out and the DeepSeek fallback never applied to the vision path.
   - After: Extraction routes by document nature — typed PDFs and DOCX go through pdfplumber/python-docx text extraction and the cheaper text LLM (Gemini with DeepSeek fallback), while only scanned/image PDFs and images use Gemini vision (with an unreadable text layer falling back to vision); the vision call disables Gemini 2.5 thinking, adds output-token headroom, and takes a configurable timeout via new `GEMINI_VISION_TIMEOUT_SECONDS` (default 240) and `GEMINI_EXTRACTION_MAX_OUTPUT_TOKENS` (default 65536).

5.

   - Before: A single LLM call on a very large (120–150+ page) document produced too-large output and hit the model's output ceiling or timed out.
   - After: The text path splits large documents into paragraph-aligned, size-bounded chunks (`_chunk_text`), extracts them in parallel with bounded concurrency, then merges and de-duplicates questions by text (`_merge_questions`); each chunk retries once on a transient error and the whole job aborts cleanly if a chunk ultimately fails (no partial quiz), tuned by new `EXTRACTION_TEXT_CHUNK_CHARS` (default 18000) and `EXTRACTION_CHUNK_CONCURRENCY` (default 4).
