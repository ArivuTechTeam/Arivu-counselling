# 7-Sep-2026

## akbar/teacher-only-content-workflow

1.

   - Before: Project documentation incorrectly suggested that institution admins and super admins could upload documents, generate quizzes, and review questions, making the intended authorization model unclear.
   - After: The documentation now states that upload, generation, and review are teacher-only workflows by design.

2.

   - Before: The teacher-only role checks in `documents.py`, `quiz.py`, and `questions.py` could be mistaken for incomplete admin support and removed later.
   - After: The existing teacher-only checks were verified and annotated with code comments that point maintainers to the documented product decision.

## akbar/ai-rate-limits

1.

   - Before: Five AI endpoints could be called without per-user hourly limits, allowing accidental or abusive usage to create uncontrolled provider load and cost.
   - After: Quiz generation, blueprint generation, topic extraction, question regeneration, and question explanation now use atomic, tenant-aware Supabase rate limiting with configurable hourly environment variables and friendly HTTP 429 responses.

2.

   - Before: Admin user pages called Supabase Auth `list_users()` once, so GoTrue's first-page limit could leave email addresses blank for users beyond the initial page.
   - After: The backend paginates through Auth users and tests cover a population above 200 accounts.

3.

   - Before: A fresh checkout did not explicitly install pytest and pull requests had no single required workflow covering backend tests, frontend lint, and frontend build.
   - After: Pytest is declared in backend requirements and `.github/workflows/ci.yml` runs all three checks for every pull request into `main`.

4.

   - Before: College setup depended on tribal knowledge about tenant creation, the first institution admin, teacher creation, and the build-time default tenant used by student signup.
   - After: `docs/onboarding-checklist.md` documents the complete repeatable onboarding flow and explains that changing `NEXT_PUBLIC_DEFAULT_TENANT_ID` requires a Vercel redeploy.

## akbar/p1-frontend-origin

1.

   - Before: The production CORS origin required by Railway was easy to leave unset or confuse with a localhost default.
   - After: The deployment runbook records `https://quiz-generator-drab-nine.vercel.app` as the required production `FRONTEND_ORIGIN` and documents how to verify it.

## akbar/p1-ai-fallback

1.

   - Before: Blueprint generation, topic extraction, and AI tutoring called Gemini directly, so a Gemini failure could take those features down even though quiz generation already supported fallback.
   - After: All three features use the shared structured completion fallback path and can fall back to DeepSeek, with tests covering primary-provider failure.

## akbar/p1-error-boundaries

1.

   - Before: Unhandled frontend exceptions displayed Next.js's generic crash experience.
   - After: Route and global error boundaries display a branded, reassuring error panel with a retry action.

## akbar/p1-upload-validation

1.

   - Before: The client advertised uploads up to 150 MB but used a 60-second request timeout and waited for the server to reject invalid size or file type.
   - After: Upload requests use a realistic extended timeout and the browser rejects unsupported types or oversized files before transferring them.

## akbar/p1-session-expiry

1.

   - Before: An API 401 immediately signed the user out and redirected to login without explaining what happened.
   - After: Expired sessions redirect with a reason and the login page clearly tells the user that the session expired and they should sign in again.

## akbar/p1-users-search-pagination

1.

   - Before: Institution admins had to work through one long user list with no search or page controls, which was impractical for 100–200 students.
   - After: The Users page supports responsive search, pagination, page-size selection, result counts, and useful empty states.

## akbar/p1-generation-load-test

1.

   - Before: Quiz generation had never been exercised with a classroom-like burst of simultaneous requests.
   - After: A repeatable load test sends 15 concurrent generation requests, verifies concurrent execution and graceful responses, and is isolated from production environment settings for CI.

## akbar/google-oauth-auth-flow

1.

   - Before: Login and signup only supported email/password authentication.
   - After: Both pages offer Google OAuth with a PKCE callback that returns users to the application correctly.

2.

   - Before: A new Google identity had no trustworthy course context and could have bypassed the existing course-derived tenant assignment flow.
   - After: Migration 14 leaves a new Google identity without application access until an authenticated database function validates an active course, derives its tenant, and creates only a student profile and enrollment; linked existing users keep their current role and tenant.

3.

   - Before: Restarting Docker Desktop served source and public environment values compiled into an older image, so local changes could appear missing.
   - After: Local Compose mounts the current frontend, backend, and read-only migrations; starts development servers; installs changed dependencies; and reloads current source and public environment values after an ordinary container restart.

4.

   - Before: Mobile login reused a reduced desktop card and did not provide a purpose-built touch and keyboard experience.
   - After: Screens below 900 px use a dedicated green hero and anchored bottom sheet with safe-area padding, 52 px controls, equal-weight password and Google actions, autofill attributes, and visual-viewport keyboard handling while desktop keeps its split-screen layout.

5.

   - Before: The initial mobile login stylesheet hid the shared signup wrapper, and desktop entrance animations could leave mobile signup fields invisible.
   - After: Mobile bottom-sheet rules are scoped to login, signup retains its responsive card, and desktop animation effects are disabled on mobile; both pages were verified at 412×915 and the compact login at 375×667.

6.

   - Before: Completed branch work had no consistent, repository-visible daily record of previous problems and resulting fixes.
   - After: `docs/akbar_changelog/` now has a documented daily-file convention with exact branch headings and numbered Before/After entries, reinforced by tracked Claude project instructions.
