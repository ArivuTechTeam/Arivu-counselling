# 8-Sep-2026

## akbar/insitute_Admin

1.

   - Before: Institution admins could create both teacher and student accounts, assign a course during creation, and delete either role from the Users page and API.
   - After: Institution admins can create and delete teachers only; students continue to join through self-signup, and the backend rejects the former student-management contract.

2.

   - Before: Teachers and students appeared together in a compact user list that did not expose the teaching hierarchy.
   - After: The page and sidebar are teacher-focused, and responsive teacher cards show identity, assigned course count, and assigned subject count with search and pagination.

3.

   - Before: An institution admin could assign teacher subjects but could not drill down from a teacher to their courses and enrolled students.
   - After: Expanding a teacher loads courses derived from explicit subject assignments; expanding a course loads its student count and a scrollable roster with names and emails.

4.

   - Before: No institution-admin endpoints exposed the teacher-to-course-to-student hierarchy.
   - After: Added `GET /api/v1/teachers/{teacher_id}/courses` and `GET /api/v1/courses/{course_id}/students`, with explicit tenant and role filters on every database query and 404 responses for cross-tenant IDs.

5.

   - Before: There were no focused regression tests for teacher-only administration or tenant-isolated hierarchy responses.
   - After: Added tests covering teacher-only lists, student exclusion, accurate student counts, cross-tenant denial, teacher-only create validation, and prevention of student deletion through the management API.

6.

   - Before: Institution admins had to invent temporary passwords manually and could not copy a newly created teacher's email and temporary password from the teacher card.
   - After: Added a secure temporary-password generator and a per-card Copy login action for credentials created during the current page session, without storing plaintext passwords in the database or exposing existing passwords.

7.

   - Before: Course and subject cards used large footer action bars, and opening a course required clicking a separate Subjects button.
   - After: The full course card now opens its subjects, the footer action bars are removed, and compact top-right delete icons on both course and subject cards retain the confirmation step.

8.

   - Before: A row with only one or two course or subject records stretched each card across a wide responsive column, making the cards much longer than the supplied reference.
   - After: Course and subject grids now use compact 280–320px auto-filled columns, matching the reference proportions while still flowing responsively on smaller screens.

9.

   - Before: Course-less teacher creation failed because Supabase applies custom app metadata after the Auth insert trigger, causing the trigger to reject the account before the backend could promote it to teacher.
   - After: Teacher provisioning now uses a validated course from the admin's tenant for safe tenant derivation, promotes the account to teacher, and immediately removes the temporary enrollment so subject assignments remain authoritative.

10.

   - Before: Institution admins created a teacher without selecting their academic access, then had to use a separate Assign action afterward.
   - After: The Add teacher form now requires a tenant-owned course and at least one subject, and provisioning saves those assignments immediately while preserving the secure tenant-derivation flow.

11.

   - Before: Teacher cards exposed an Assign button that could only change subjects; the teacher's name and sign-in email could not be maintained from this page.
   - After: Each card now has an edit icon opening one editor for name, email, courses, and subjects; the backend updates Supabase Auth, the tenant-scoped profile, and derived course access with best-effort rollback if a later step fails.

12.

   - Before: Teachers were returned in database default order, so a newly created account could appear at the bottom or on a later page.
   - After: The teacher API sorts profiles by `created_at` descending, placing newly created teachers first and returning the timestamp explicitly.

13.

   - Before: Adding or editing a teacher only changed the page contents or displayed an inline error, which made the action result easy to miss.
   - After: Successful and failed add/edit actions now show a dismissible, accessible notification with a clear result message.

14.

   - Before: Removing a teacher who had uploaded documents or created/reviewed questions and quiz sets failed because those records used restrictive profile foreign keys, and the failure appeared inside the Add teacher form.
   - After: Migration 20 preserves institutional academic content by clearing deleted-author references, while teacher deletion now reports success or failure in the same accessible pop-up notification used by other teacher actions.

15.

   - Before: Copy login became disabled after a page refresh because the temporary password existed only in browser memory and Supabase passwords cannot be read back from their hashes.
   - After: Copy login remains available on every teacher card; when the password is no longer in memory, it asks the admin to confirm a secure temporary-password reset, marks the teacher for a first-login password change, and copies the new credentials without storing plaintext in the database.

16.

   - Before: The institution-admin quiz API returned only basic quiz metadata, leaving the UI without engagement, accuracy, publication, review, teacher, course, or last-attempt information.
   - After: The API returns tenant-scoped teacher/course IDs, graded attempt count, weighted average accuracy, publication and last-attempt dates, and per-status question review counts, ordered newest first.

17.

   - Before: The Quizzes page only supported text search and gave administrators no way to isolate a teacher, course, lifecycle status, or performance problem.
   - After: The page now provides live teacher, course, and status filters; seven useful sort orders; URL-persisted filter state; and clear no-attempt, low-engagement, active, and pending-review health badges.

18.

   - Before: Quiz rows showed no performance context and could not reveal which students or questions were struggling.
   - After: Accessible quiz cards display attempts, accuracy, question count, status, and health; selecting one opens a detailed modal with type/difficulty breakdowns, graded student submissions, and the five weakest answered questions.

19.

   - Before: Course Performance and Teacher Activity on Analytics were static summaries with no path to the underlying quizzes.
   - After: Course rows and teacher activity controls now open tenant-filtered quiz drill-downs showing engagement, accuracy, status, ownership, and last-attempt date, with a second click opening the full quiz performance view.

20.

   - Before: Quiz performance aggregation and its role-specific route registration had no focused tenant-isolation regression coverage.
   - After: Tests now verify weighted metrics, review counts, detailed student/question output, tenant scoping on every related database query, and registration of both summary and detail API routes.

21.

   - Before: Institution admins could inspect individual quiz performance but had no consolidated view of teacher publishing activity, engagement, or student outcomes.
   - After: Added a tenant-scoped faculty analytics endpoint that includes every teacher, 30-day activity status, created and published quiz counts, all-attempt engagement, weighted graded accuracy, last-created date, course names, and institution totals.

22.

   - Before: The Quizzes page opened directly into filters and quiz cards without showing which faculty members were active or needed attention.
   - After: A prominent Faculty Performance card now summarizes six institution metrics and previews the top three teachers, opening a sortable faculty dashboard with clear activity-health indicators.

23.

   - Before: Administrators could not move directly from a faculty metric to that teacher's underlying quizzes.
   - After: Faculty rows open a teacher quiz sub-view with performance, detail, and download actions while simultaneously applying the teacher filter to the main page through the tenant-safe `teacher_id` quiz API filter.

24.

   - Before: The Quizzes tab used one oversized institution-wide Faculty Analysis card and a second modal, repeating summary information before administrators could reach an individual teacher's quizzes.
   - After: The tab now opens on a clean grid of rectangular cards, one per faculty member, with quiz count, published count, attempts, weighted accuracy, activity health, courses, and last-created date; selecting a card opens that faculty member's quizzes in place with a clear back action and removes repeated teacher labels from their quiz cards.
