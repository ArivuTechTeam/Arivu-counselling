# Akbar changelog — 11 Sep 2026

## fix/student-dashboard-audit

1.

   - Before: Challenge links were lost during login, any same-institution student could access another course's challenge, only mutable question ids were frozen, requested question counts could silently shrink, and concurrent accepts could create duplicate attempts.
   - After: Safe challenge return paths survive password and Google login, new challenges record every required course and an immutable question snapshot, students choose an exact mix of Single Choice, Multiple Choice, True/False, Numerical, and Fill-in-the-Blank questions, and a partial unique index limits each participant to one session per challenge.

2.

   - Before: Creating a challenge immediately consumed the creator's attempt, so the creator could not create/share a game now and play later; challenge sessions were also untimed.
   - After: Creation writes only the frozen game and opens its shareable lobby. The creator and friends start their own single attempt later, at which point the server-enforced type-based timer begins; start returns the complete answer-stripped state for immediate cached navigation.

3.

   - Before: Students received no one-attempt warning before starting, creators could not recover unfinished challenges, links never closed or expired, and equal scores had unstable ordering.
   - After: Starting an attempt uses the shared readiness warning, creators get a My Challenges list with recovery, copy-link, and close controls, the lobby has explicit back navigation and pre-play link sharing, sharing expires after `CHALLENGE_EXPIRY_DAYS`, and standings use score followed by elapsed time and stable submission ordering.

4.

   - Challenge sessions no longer appear in Quiz History because their results and participants live in My Challenges. Result review displays the stored question explanation only for incorrect answers and no longer offers the AI Tutor action.

5.

   - Verification covers create-without-attempt → share → creator/friend start → deterministic grade → leaderboard, immutable-snapshot grading, exact type-mix shortages, course rejection, single-attempt rejection, expiry/closure behavior, and migration security assertions. No AI provider is called by challenge selection, grading, or result explanations.

6.

   - Before: Migration 27 left behind a service-role helper for the superseded create-and-start-together challenge flow.
   - After: Migration 28 removes that obsolete helper so the database surface matches the finalized create-link-first, play-later game lifecycle.

## fix/supabase-connection-resilience

1.

   - Before: Concurrent Supabase reads shared the SDK's default HTTP/2 transport, and a terminated multiplexed connection could escape as an HTTP 500 without recovering.
   - After: Stateless backend Supabase clients use a bounded HTTP/1.1 keep-alive pool and retry only idempotent reads after transient transport or gateway failures; writes remain non-retried to prevent duplicate quiz operations.

2.

   - Before: A Supabase read that remained unavailable after the SDK call failed produced an unexplained server error, and every authorization lookup selected the complete profile row.
   - After: Exhausted safe retries return a retryable HTTP 503 with `Retry-After`, transport retries are logged without credentials, and authorization selects only the required profile fields.

## perf/non-student-dashboard-speed

1.

   - Before: **Confirmed** — the institution-admin landing page requested `/admin/overview`, `/admin/analytics`, and `/admin/quiz-sets`; the first two independently scanned nearly the same tenant data. Including authorization, this was 22 database round trips per cold landing load.
   - After: **Confirmed** — the analytics response now includes the small content counters the landing page needs, so the duplicate overview request is removed. The cold landing path is 2 API requests and 13 database round trips, while analytics and quiz pages reuse the same 60-second SWR cache.

2.

   - Before: **Confirmed** — the faculty landing page fetched class analytics, documents, and quiz sets separately (11 database round trips including authorization), and six dependent class-overview reads waited one after another.
   - After: **Confirmed** — one tenant- and teacher-scoped class-overview response supplies both analytics and content counters (8 database round trips including authorization). Independent reads overlap in four dependency stages, and the two landing-page components share one SWR request.

3.

   - Before: **Confirmed** — `/courses` fetched subjects once per course, making its query count grow as `courses + 3` for institution admins and `courses + 2` for faculty.
   - After: **Confirmed** — one tenant-scoped `.in_("course_id", ...)` query loads all relevant subjects. The endpoint now stays at 4 application queries for institution admins and 3 for faculty regardless of course count, with a regression test proving one subject query across three courses.

4.

   - Before: **Confirmed** — the super-admin overview ran seven independent, paginated platform reads serially; returning to Institutions, Question Quality, or Question Bank also started from an empty component state.
   - After: **Confirmed** — the seven overview reads run concurrently through the existing thread-safe HTTP/1.1 Supabase pool, and shared SWR keys preserve/reuse results across super-admin pages. A controlled 50 ms-per-read benchmark improved from 0.362 s serial to 0.055 s concurrent (6.5×); real production latency will depend on database size and network conditions.

5.

   - Before: **Confirmed** — faculty Class Monitor, Subjects, Documents, quiz lists and course selectors, plus institution Users/Analytics/Quiz pages, used isolated mount-time fetching and showed full loading states again when revisited.
   - After: **Confirmed** — staff read models use stable role-scoped SWR keys with the dashboard's existing 60-second deduplication, previous-data retention, explicit retries, and mutation refreshes. No AI generation, extraction, quiz selection, or grading path was changed.

6.

   - Before: **Probable** — single-column indexes required extra filtering work for the compound tenant/role/owner/status access patterns used by growing staff dashboards.
   - After: **Confirmed in code, pending database application** — migration 29 adds non-destructive composite indexes for those exact tenant-scoped filters. It must be run in Supabase before production receives the database-side benefit; no migration was applied automatically.

## fix/app-wide-reliability-audit

1.

   - Before: Generic frontend fetch errors could not be correlated with a specific backend request, and unexpected 500 responses had no safe support reference.
   - After: Frontend and backend propagate a validated request ID, API completion logs include duration/status, CORS exposes diagnostic headers, and typed frontend errors distinguish timeout, network, authorization, rate-limit, unavailable-service, and server failures.

2.

   - Before: A normal browser request timed out after 20 seconds while a single Supabase read could wait 30 seconds before its first retry, so the browser could show “Try again” before backend recovery began.
   - After: `SUPABASE_READ_TIMEOUT_SECONDS` defaults to five seconds so bounded read retries finish within the browser deadline, and the frontend retries one time only for safe GET transport/502/503/504 failures; writes are never replayed.

3.

   - A no-AI four-role audit passed 77 local API journey checks and 84 focused regression tests plus 40 subtests. Live staged load passed 1,005/1,005 requests through 150 concurrent workers; a 330.968-second soak passed 3,373/3,375 requests and exposed two simultaneous 30-second reads that motivated the timeout fix. Full evidence and verification boundaries are recorded in `docs/reliability-audit-11-Sep-2026.md`.

4.

   - A follow-up no-AI capacity run used 200 unique temporary student accounts. The 200-user dashboard burst passed 600/600 backend requests but reached 18.473-second p95, so the protective limit stopped write-heavy testing at that level; the complete eight-page tour and quiz start/submit passed at 100 concurrent unique students. All temporary users and tenant data were removed.
