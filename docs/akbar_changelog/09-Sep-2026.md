# 9-Sep-2026

## akbar/api-leak-hardening

1.

   - Before: Authenticated students could bypass FastAPI and read answer-bearing Supabase tables, including question answers, explanations, and quiz-to-question mappings, while tenant profile rows were visible beyond the signed-in user.
   - After: Migration 22 limits browser database access to the caller's own profile and the Google onboarding RPC, revokes direct access to application tables, and preserves all content access through the role-checked, tenant-scoped backend.

2.

   - Before: Both analytics views were anonymously readable through Supabase PostgREST and ordinary view-owner execution could bypass the underlying tables' RLS context.
   - After: Both analytics views use `security_invoker`, deny `anon` and `authenticated` access, and remain available only to the backend service role.

3.

   - Before: The local development account switcher compiled account passwords from a `NEXT_PUBLIC_*` variable into browser JavaScript, where anyone using that build could inspect them.
   - After: Development configuration contains email labels only and requires the developer to enter the password at sign-in time; the old password-bearing environment variable was removed from the example and local configuration.

4.

   - Before: Several API failures returned raw provider, database, or exception messages, and extraction jobs persisted raw exception text that could later surface through diagnostics.
   - After: API failures return stable user-safe messages, validation responses omit submitted values, extraction records store generic failure text, and server logs record only the operation and exception class.

5.

   - Before: Production could expose FastAPI schema documentation, accept any localhost origin through CORS, cache authenticated responses without an explicit prohibition, and return temporary teacher credentials without an explicit response contract.
   - After: API docs and localhost CORS are development-only, authenticated API responses use `no-store`, CORS uses the configured production origin, and temporary teacher credentials have a narrow response model with cache prevention.

6.

   - Before: Teacher review and blueprint reads selected complete database rows, including internal fields the operation did not require.
   - After: These reads request only the fields needed to generate or render the response, reducing accidental payload expansion and keeping internal columns server-side.

7.

   - Before: Production rollout and network-tab verification steps for the API boundary were undocumented.
   - After: Added a security rollout guide with the required Supabase migration, Railway and Vercel settings, password-rotation guidance, privilege verification SQL, and browser Network-tab expectations.

## akbar/document-pavyaa-integration

1.

   - Before: Pavyaa's document feature was based on an older `main`, conflicted with the API-security work, and could overwrite safe errors, tenant filtering, CORS controls, and newer dashboard API types during a merge.
   - After: Integrated the complete document feature onto current `main`, resolved every overlap by retaining both feature behavior and security controls, and reduced document reads to the required columns.

2.

   - Before: Teachers could not review their upload history, reopen the original private file, or retry a failed extraction without uploading the file again.
   - After: Added a teacher-only Document Log with subject/chapter and quiz status, five-minute owner-scoped signed file links, and rate-limited retry using the stored document and assignment context.

3.

   - Before: Typed PDFs were sent through the slower vision path, large text documents depended on one oversized model call, and transient extraction failures ended the workflow.
   - After: Typed PDF/DOCX extraction uses Gemini with DeepSeek fallback, scanned files use configurable Gemini vision, large text is processed in bounded concurrent chunks with retry and de-duplication, and failed jobs retain safe retry context.

4.

   - Before: The document-link schema change reused migration number 20, was absent from `schema.sql`, and would collide with the already-applied teacher-retention migration.
   - After: Renamed the additive change to migration 23, synchronized the baseline schema and deployment documentation, and indexed `(tenant_id, document_id)` for tenant-scoped document-log lookups.

5.

   - Before: New extraction settings were undocumented and accepted invalid numeric values, while the branch's new tests failed in fresh CI environments without Supabase secrets.
   - After: Documented and validated all four extraction settings, isolated tests from environment secrets, and added focused coverage for migration numbering, tenant-scoped logs, signed URLs, and retry authorization.

6.

   - Before: Duplicate-file detection could disclose another teacher's matching filename/date inside the same tenant, and some extraction updates and compensating deletes relied only on globally unique IDs.
   - After: Duplicate detection is owner-scoped, and document, extraction-job, quiz-set, and question mutations repeat the verified tenant and owner filters when using the service-role client.

7.

   - Before: The browser requested a signed URL asynchronously and then opened a new tab, which could be blocked by popup protection.
   - After: The click reserves a safe blank tab before the API request, navigates it after receiving the signed URL, and falls back to same-tab navigation when a popup cannot be opened.

## akbar/notify-pavyaa-integration

1.

   - Before: Pavyaa's notification branch was 24 commits behind `main` and conflicted with the newer safe API-error handling, tenant filters, and weighted teacher-accuracy calculations.
   - After: Integrated the notification work onto current `main`, resolved both backend conflicts, retained safe public errors and explicit tenant scoping, and kept accuracy weighted by earned marks over possible marks.

2.

   - Before: Review actions and successful generation, extraction, approval, and publishing operations had little visible confirmation.
   - After: Added accessible in-card approval/rejection feedback, reduced-motion-aware animations, celebratory effects for major actions, and a dashboard-level toast system for one-off success messages.

3.

   - Before: The temporary-password flow accepted weak replacements, did not verify the current password, and left first-login users inside a stale authenticated session.
   - After: The backend verifies the current password, enforces the documented strength policy without exposing provider errors, tenant-scopes the profile unlock, and the frontend signs forced-change users out with a clear message before they log in again.

4.

   - Before: Google-only accounts were offered a password-change form that required a current email/password credential they did not have.
   - After: The dashboard detects whether the authenticated Supabase account has an email identity and only offers the current-password flow when that credential exists.

5.

   - Before: Teacher subject analytics included other teachers' quizzes and questions from shared subjects, counted unfinished attempts, and averaged percentages in a way that could disagree with the rest of the platform.
   - After: Subject metrics use only the signed-in teacher's content and graded attempts, every service-role query is tenant-scoped, and subject plus overall accuracy use total earned marks divided by total possible marks.

6.

   - Before: Teacher dashboards did not show a 14-day attempt trend, score distribution, or per-subject operational metrics, and the new aggregation behavior lacked isolation tests.
   - After: Added the teacher trend, score distribution, subject KPI cards, pending-review indicators, and a regression test proving tenant filters, teacher ownership, graded-attempt filtering, and weighted accuracy.
