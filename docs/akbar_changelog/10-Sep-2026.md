# 10-Sep-2026

## fix/student-dashboard-audit

1.

   - Before: Dashboard totals, Weak Areas, and Revision analyzed only teacher-published quiz attempts, so Smart Quiz, Daily Challenge, Exam, Challenge, and practice results were absent even though History displayed them.
   - After: Student analytics combine graded answers from both quiz engines with explicit student and tenant scoping, and the Weak Areas UI retains weak topics even when stronger sibling topics lift the subject average.

2.

   - Before: A course leaderboard counted all work completed by enrolled students, including quiz and practice results from other courses, and treated score percentage as answer accuracy.
   - After: Leaderboard work is attributed to the selected course through its subject and chapter relationships, ambiguous unscoped work is not duplicated across multi-course students, and accuracy is computed from correct versus answered questions.

3.

   - Before: Starting a published variant with no approved questions created an empty attempt that could crash the quiz-taking screen, and the immediate submission result used a generic quiz title.
   - After: Empty variants are rejected before attempt creation, the client safely handles an empty response, and both submitted and reloaded results contain the tenant-scoped quiz title.

4.

   - Before: The generic practice endpoint accepted reserved modes such as exam, daily, and challenge, allowing their dedicated setup rules to be bypassed; an expired exam could still autosave, while final submission discarded answers saved before expiry.
   - After: Generic practice accepts only smart, chapter, and revision modes, expired exams reject new autosaves, and expiry grading uses only the last server-side autosave made before the deadline.

5.

   - Before: A student could bookmark any approved question in their institution and use Revision to reveal its answer without having attempted it.
   - After: Bookmark and explanation access share one authorization check requiring that the student submitted the question in a graded quiz or practice session.

6.

   - Before: Several challenge, result, and compensating-write lookups relied on globally unique identifiers without repeating the authenticated tenant boundary.
   - After: Challenge tokens, participant names, answer reads, rollback deletes, and attempt/session updates repeat tenant and student ownership filters when using the service-role client.

7.

   - Before: Daily Challenge displayed a bare error, Exam Simulator could remain on a loading skeleton after a failed configuration request, and Smart Quiz offered no retry when its initial content request failed.
   - After: All three pages render explicit retryable error states while preserving separate start-action errors and their existing loading and empty states.

8.

   - Before: Student grading, cross-engine analytics, course leaderboard attribution, challenge tenancy, reserved practice modes, exam expiry, and cross-student attempt ownership lacked one focused regression suite.
   - After: Added deterministic tests for every supported question type and the full start, take, submit, grade, result, history, and ownership flow, plus focused analytics and authorization coverage.

9.

   - Before: The Subjects screenshot showed `/api/v1/quizzes` taking 6.19–12.79 seconds and eventually surfacing the generic 20-second client timeout because quiz variants and question counts were loaded through nested database queries.
   - After: The audit branch now includes the batched quiz-catalog implementation; the same configured `sri@gmail.com` account returns 11 quiz sets in 1.35 seconds in a read-only live-data benchmark, with the catalog path reduced from 33 to seven database round trips in the regression fixture.

10.

   - Before: Dashboard, Subjects, Smart Quiz, and Challenge each mounted an independent `/api/v1/quizzes` request, amplified by duplicate development-mode mounts and repeated navigation.
   - After: All four consumers share one SWR quiz-catalog key, so an in-flight request is deduplicated and navigation within the 60-second dashboard cache window reuses the loaded catalog instead of starting over; quiz submission clears catalog and dashboard summaries so completed-attempt data never remains stale.

11.

   - Before: Student endpoints constructed new Supabase clients and HTTP pools per call, adding connection setup to already query-heavy Stats, Weak Areas, Revision, History, and Leaderboard requests.
   - After: Stateless Supabase clients and their connection pools are reused safely, while password authentication remains isolated because it mutates session headers; live read-only checks returned every inspected student endpoint successfully and loaded the exact 15-question practice session in 277–437 ms.

12.

   - Before: The student-page Network trace still showed duplicate successful GETs during development mounts and navigation, including Leaderboard at 3.06 and 5.45 seconds, Revision Topics at 1.99 and 3.47 seconds, Bookmarks at 0.51 and 1.64 seconds, Daily at 0.87 and 1.21 seconds, and Exam Config at 0.55 and 0.86 seconds.
   - After: Dashboard, History, Daily, Revision, Weak Areas, Leaderboard, Exam, and Challenge now use shared student-specific SWR keys under the dashboard's 60-second dedupe window, eliminating duplicate in-flight requests and rendering cached data immediately when returning to a page.

13.

   - Before: Broad client caching could have made recently graded scores, attempt history, weak areas, revision topics, daily streaks, challenge standings, or course rankings remain stale until the cache window expired.
   - After: Quiz and practice submission explicitly evict every attempt-derived student cache, bookmark saves evict Revision bookmarks, and Daily/Challenge starts evict their active-state cache; live route checks returned Exam HTTP 200 in 0.16 seconds and backend health HTTP 200 in 0.02 seconds.

14.

   - Before: A 100-question attempt rendered its question palette as five narrow columns in a 256px sidebar, forcing the student to scroll through roughly twenty rows while much of the desktop content width remained unused.
   - After: Attempt and practice routes use a wider 1440px workspace with a compact ten-column desktop palette, smaller accessible number controls, horizontal status legend, and combined progress/submit row, keeping all 100 question numbers visible together in roughly ten rows without an internal palette scrollbar.

15.

   - Before: Starting a published quiz loaded its approved questions during the POST only to discard them, then the attempt page repeated three database reads before rendering; practice question loading also selected every column, including each unused 1536-dimensional embedding.
   - After: New quiz and Smart Quiz responses include the already-loaded answer-stripped taking state and prime exactly one client-side route transition, reducing the regular start path from ten to seven measured database round trips and removing the immediate duplicate GET; practice loads only the seven fields needed for taking and grading, and opening an attempt no longer writes an empty autosave before the student edits an answer.

16.

   - Before: The fixed 22rem, ten-column question palette made a ten-question quiz look oversized and unnecessarily reduced the width available to the question card.
   - After: The palette now responds to quiz length: 1–5 questions use a compact 14rem/five-column layout, 6–20 use 16rem/five columns, 21–50 use 20rem/eight columns, and larger exams retain the ten-column palette. Short quizzes gain content space while large exams remain visible without internal scrolling.

## fix/dashboard-client-cache

1.

   - Before: Student, teacher, institution-admin, and super-admin landing dashboards unconditionally fetched their complete payload again whenever their components remounted.
   - After: SWR caches each role dashboard payload inside the authenticated dashboard layout, deduplicates requests for 60 seconds, renders cached data immediately on return navigation, and discards the cache when the dashboard session unmounts.

2.

   - Before: `html-to-image` was part of every quiz attempt's initial JavaScript even though students only use it after grading when downloading a score card; attempt and practice routes each loaded 192 kB initially.
   - After: `html-to-image` loads only when image export is requested, reducing the measured first-load JavaScript for both attempt routes from 192 kB to 187 kB.

3.

   - Before: The codebase had no server-state cache package, and adopting a larger mutation-oriented query framework would add configuration beyond these read-heavy dashboards' needs.
   - After: Added SWR as the lightweight fit for cached GET requests, retaining existing retry UI and parallel fetch behavior without a global query-client setup.

4.

   - Before: Findings #3 (super-admin aggregation) and #5 (missing indexes) were identified alongside the current performance work.
   - After: Both performance findings remain explicitly pending for the requested follow-up round and are unchanged on this branch.

## fix/student-dashboard-query-batching

1.

   - Before: Listing four published quiz sets with twelve variants made 33 Supabase round trips because variants and approved questions were loaded inside nested loops.
   - After: Variants and approved-question links are fetched with two batched `in_()` queries, reducing the measured catalog request to seven total database round trips independent of the number of sets and variants.

2.

   - Before: Loading approved attempt questions selected every question column, including the unused 1536-dimensional embedding.
   - After: Attempt loading selects only id, type, text, options, correct answer, explanation, and marks; count-only dashboard loading selects only linked ids.

3.

   - Before: Findings #3 (super-admin aggregation) and #5 (missing indexes) were identified alongside the current performance work.
   - After: Both findings remain explicitly pending for the requested follow-up round and are unchanged on this branch.

## fix/supabase-client-singletons

1.

   - Before: Two calls each to `get_service_client()` and `get_anon_client()` constructed four Supabase clients and four separate HTTP connection pools.
   - After: Each stateless accessor lazily creates one process-wide client, reducing the measured construction count from four to two and allowing HTTP connections to be reused across requests.

2.

   - Before: A naive anon-client singleton would allow `sign_in_with_password` to mutate shared session storage and Authorization headers, creating a concurrent cross-user state risk.
   - After: Password verification uses an explicitly isolated anon auth client, while only stateless clients are shared; a 40-call, 20-thread test confirms concurrent first access constructs exactly one service client.

3.

   - Before: Findings #3 (super-admin aggregation) and #5 (missing indexes) were identified alongside the current performance work.
   - After: Both findings remain explicitly pending for the requested follow-up round and are unchanged on this branch.
